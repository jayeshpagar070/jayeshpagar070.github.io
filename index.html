1 · Context: two systems that must tell the same story

The product: myEcodev

A web platform for autodemolitori, the yards that scrap end-of-life vehicles. It handles intake, scrapping certificates, de-registration from the PRA and RVFU registers, spare parts, invoicing and the legal waste paperwork. The interface is entirely in Italian.

The regulator: RENTRI

Italy's national electronic register for waste traceability, run for the Ministry of Environment. Waste transport forms (FIR) are now issued digitally as xFIR documents and move through a signed life cycle: producer, transporter, receiver.

The risk

An end-of-life car is hazardous waste (EER 16 01 04*). If the form in myEcodev, the record on RENTRI and the official PDF disagree, the yard is carrying a legally wrong document. A sync bug here has legal consequences.

Digital FIR life cycle on RENTRI (simplified from about 20 states)

Draft→Producer signs→In transport→Transhipment→Receiver acceptance→Accepted · Partly rejected · Rejectedor Cancelled

2 · Starting point: no domain knowledge, no tests, two live portals

When I joined, the automation repository held the Playwright template and an empty seed file. There were no test plans and no user stories. The business rules lived in Italian legislation, the RENTRI OpenAPI spec and the heads of the developers.

  • Language and domain. Italian UI, legal terms (Formulario, Registro carico/scarico, MUD, Albo), and a regulator API with JWT auth, asynchronous operations and a rate limit of 100 requests per 5 seconds.
  • Two-sided truth. Each test has to drive myEcodev, then confirm the result on the RENTRI operator portal, then read the official PDF. A pass in one system proves nothing on its own.
  • Irreversible actions. Generating, signing or cancelling a FIR on RENTRI can't be undone, and some steps need a signing device the demo login does not have. The test design had to work around those steps without guessing.

  • Domain ramp-up in one day. Used AI-guided, read-only walkthroughs to map every module, the 8-tab vehicle file and the FIR screen. Wrote a 60-term Italian–English glossary and a RENTRI API guide that now serve as onboarding material.

5 · Impact and scale: why the approach holds up

Impact
  • Data errors that would put wrong legal documents in front of inspectors were found before more customers hit them.
  • Developers receive cards they can act on directly: exact steps, environment, expected versus actual, and a video.
  • The product owner gets a ranked roadmap toward full RENTRI parity, with open decisions listed separately.
  • Client tickets get a clear answer: product bug or account setup. That saves support and development time.
Scalability
  • A new user story enters the same pipeline. The prompt, page objects and evidence format are reused unchanged.
  • The healer agent repairs locator drift, so a UI change costs minutes of maintenance instead of hours.
  • The cross-check pattern (local app, regulator, PDF) carries over to the waste register, the MUD declaration and the RVFU vehicle register.
  • Persistent memory keeps hard-won rules, so the next session or the next engineer starts with them.

6 · Lessons: what I'd tell the next team

Make AI tag its claims

Asking agents to separate verified behaviour from assumptions kept unproven requirements out of the acceptance criteria.

Encode the rules, not just the steps

Most early failures came from domain rules, such as past dates switching a form into historical mode. Writing those rules into memory stopped the same mistake from repeating.

Keep humans on irreversible actions

Signing, cancelling and product-rule decisions stayed with people. The AI prepares the evidence and a person makes the call.

Client names, credentials and internal identifiers are left out. All testing ran on the myEcodev test instance and the RENTRI demo environment.

The agentic transformation

Treat each QA role as an AI agent with its own tools, its own rules and its own output file. A human stays in the loop as the reviewer and decision-maker.

Why a pipeline of agents, and not one big agent?

Separation of concerns

Each agent has a narrow job, a restricted tool list and explicit rules. The Story Analyst has no device access by design, so it cannot "fill gaps" by guessing.

Auditable hand-offs

Every step writes a file that the next step consumes (qa/01 → qa/02 → qa/03 → qa/04 → src/tests → test-results → qa/06). Any number in the final report can be traced back to its source.

Least privilege

The Planner may look at the device but not drive flows. The Healer may edit code but has a hard rule against touching assertions.

Cheaper models where possible

Sub-agents run on a faster model; the orchestrator keeps the expensive reasoning.

The seven agents

Each agent is a Markdown definition in .claude/agents/ with front-matter (name, description, allowed tools, model) and a body of operating rules.

Design choice: Playwright's built-in planner/generator/healer agents are bound to browser tools and cannot drive a native app. This project re-implements the same three roles for Android and adds four more (BA, Analyst, Exploratory, Reporter). Browser concepts with no Android equivalent are replaced: page refresh → app relaunch, storageState → device enrolment fixtures, network interception → real backend + device-state steps.

Framework engineering – the deterministic layer the agents build on

A Page Object Model designed for AI generation: one small, consistent contract means a generated page object looks like a hand-written one, and the healer always knows where a locator lives.

export abstract class BasePage {
  /** A locator present only on this screen. Used to decide "am I here yet?". */
  protected abstract readonly identifier: Locator;

  async waitUntilLoaded(timeout = 15_000) { await this.identifier.waitFor({ state: 'visible', timeout }); return this; }

  /** Matches both native "pkg:id/x" and React Native bare testID "x". */
  protected byId(name: string): Locator {
    return this.screen.getByTestId(name).or(this.screen.getByTestId(resId(name)));
  }
}
AI-readable failure evidence

viewTree: 'on-failure' attaches the accessibility tree to each failed test – this is what the Healer reads. JSON reporter for agents, HTML for humans; device-log.ts pulls logcat and the crash buffer, because on Android the "console" lives outside the test process.

Preflight: fail loudly

global-setup.ts blocks the run if the .env is missing, the driver is dead, the device is ambiguous or offline, or the app is not installed. Each had earlier shown up as a fake app defect – e.g. 20 tests silently skipped with exit 0, or 17 "failures" in 18 ms each.

Self-healing infrastructure

A driver supervisor keeps the mobilecli driver alive and restarts it within about 1 s; with retries: 1 a transient disconnect recovers on its own. A UiAutomator fallback reads elements the accessibility API cannot see (NAF-flagged MPIN boxes). Device targeting resolves name → serial so a run never executes on the wrong device.

Domain helpers

Arithmetic-captcha solver; human-in-the-loop OTP hand-off (opt-in, so CI never hangs); copy-quality audit via nspell; PIN/OTP box and soft-keyboard handling; and APK intake – drop a new APK in apps/ and it reinstalls cleanly and writes app.json. No config edit per build.

Ordered, state-aware regression

run-ordered.mjs runs the 16 suites in customer-journey order and inserts device-state steps between them (reinstall before Quick Deposit, re-enrol before Profile), so every suite starts from the state it needs.

Known-defect strategy

Tests that reproduce an open bug are tagged @known-defect. npm run test:gate is the release gate and excludes them; npm run test:known-defects re-verifies them on each new build. Defects stay visible without blocking the pipeline.

Responsible-AI guardrails

The agents are deliberately constrained. These rules came from real incidents during the project:

Evidence tagging ([NOT VERIFIED], [GAP])Stops the LLM from inventing acceptance criteria to fill a template
No assertion weakening in healingA green run with a hidden defect is the worst outcome the pipeline can produce
Defect / Plan error / Environment triageKeeps flaky infrastructure out of the defect log

End-to-end example: Fund Transfer module

  1. QA lead: "Run the pipeline for Fund Transfer."
  2. BA Explorer walks Own-Account, Other-Account, IMPS and NEFT screens on the device and writes US_007 with evidence. It flags beneficiary limits it could not trigger as [GAP].
  3. Story Analyst models the Beneficiary entity (Create/Modify/Close), the transfer state machine, and limit/PIN rules.
  4. Test Planner produces 60+ cases, including rotation mid-form, process death on the OTP screen and offline submit.
  5. Exploratory Tester executes them on the phone. It finds, among others, that IMPS and NEFT "Close Beneficiary" ask for a Transaction PIN but offer no "Forget Transaction PIN?" link, and logs both with screenshots.
  6. Test Generator writes the IMPS/NEFT page objects and 14-fund-transfer.spec.ts (64 tests); the two findings become @known-defect tests.
  7. Test Healer fixes two locators broken by a build change and refuses to touch the known-defect assertions.
  8. QA Reporter publishes US_007-test-report.md and US_007-defects.xlsx for the development team.
